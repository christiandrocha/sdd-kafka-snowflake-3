## Part 2 — SDD lifecycle (`.claude/sdd/README.md`)

### Spec-Driven Development — how this repository is built

Every change to this repository goes through a written spec before code, and through an
independent, measured validation after code. This file is the process; `CONSTITUTION.md`
is the rules that hold in every phase; `_index.md` is the live status.

#### Lifecycle

| # | Phase | Artifact (in `features/<FEATURE>/`) | Exit gate |
|---|-------|-------------------------------------|-----------|
| 0 | Brainstorm | `BRAINSTORM_<FEATURE>.md` | A direction is chosen. *Optional for small features.* |
| 1 | Define | `DEFINE_<FEATURE>.md` | Approved. Clarity ≥ 12/15. **Scope freezes here.** |
| 2 | Design | `DESIGN_<FEATURE>.md` | Independent design review recorded (second opinion). |
| 3 | Build | code + `BUILD_REPORT_<FEATURE>.md` | CI green. Every PR cites a `REQ-xx`. |
| 4 | Validate | `VALIDATION_<FEATURE>.md` | Every acceptance test has a **measured** result, by a reviewer who did not build it. |
| 5 | Ship | `SHIPPED_<YYYY-MM-DD>.md` | Ship gates checked; durable decisions promoted to ADRs; folder moved to `archive/`. |
| 6 | Retro | `RETRO_<FEATURE>.md` | Its *Changes Applied* diff is merged. Part of the Ship gate. |

Templates live in `templates/`. Brainstorms not yet promoted live in `backlog/`.

#### Where a decision lives

- **While a feature is active**, a decision lives inline in its DESIGN, under *Key Decisions*,
  next to the code it shapes.
- **At Ship**, every decision with lasting value is promoted to a numbered ADR in `docs/adr/`,
  and the DESIGN links to it. From then on the ADR is the single source of truth.
- A decision that only made sense inside the feature stays in the archived DESIGN.

#### Fast track

A change qualifies when it touches no schema, no data contract and no infrastructure, and fits
in one small PR. It skips Brainstorm and Design — **never** the mini-DEFINE (one paragraph +
one acceptance test, in `_index.md`) and **never** Validate. The Constitution applies in full.

#### Parallel work

- A feature folder is the unit of parallelism. An agent working on a feature loads only that
  folder, `CLAUDE.md`, `CONSTITUTION.md` and the skills listed in its DEFINE.
- Two features may run in parallel only if their **File Ownership** sets do not intersect.
- One git worktree / branch per feature. Integration happens only through PR + CI.
- Files listed as *Shared — serialize* in `_index.md` have one writer at a time.
- The practical limit is review bandwidth, not agents: no more features in Build than the
  owner can review the same day.

#### What the client sees (when this blueprint is used on an engagement)

The client approves the **DEFINE** and receives the **Ship** (code, runbooks, validation
evidence). Brainstorm, design review and retro are internal working practice.

#### Principles

| # | Principle | Meaning |

| P1 | Spec before code | No Build without an approved DEFINE and a reviewed DESIGN (fast track: mini-DEFINE). |
| P2 | Measure, don't claim | A cost, performance or correctness statement in the README needs a query or test that reproduces it. |

#### Hard rules for agents

| # | Rule |
|---|------|
| R1 | **Never** run `terraform apply`, `terraform destroy`, or any `DROP`, `TRUNCATE`, `DELETE` without `WHERE`, `ALTER ... SUSPEND` on shared objects. Agents run `terraform plan` and propose; `apply` happens only through the CI pipeline with approval. |
| R2 | **Never** hold or request production credentials. Agents work against the dev environment only. |
| R3 | **Never** print, write or commit secrets. Read them from environment variables; never read the secret store contents into context. |
| R4 | **Always** present a plan before multi-file or multi-step changes, and wait for approval. |
| R5 | **Always** cite a `REQ-xx` in every commit/PR. No requirement, no change. |
| R6 | **Never** modify a file owned by another active feature (see `_index.md`). Shared files: one writer at a time. |
| R7 | If the request scores below 3/5 on clarity (goal, scope, acceptance), ask before planning. |
| R8 | When unsure whether an action is reversible, treat it as irreversible and ask. |

#### Data rules

| # | Rule |
|---|------|
| D1 | No real personal data in prompts, fixtures or test data. Synthetic only. |
| D2 | Columns holding personal data are tagged and masked before any new consumer reads them. |

### DEFINE: Cost Governance 2.0 (COST_GOVERNANCE)

> Cut the part of the Snowflake bill that is warehouse uptime rather than query execution,

#### Problem Statement

v2 measured it on its own invoice: on 2026-08-11, `CDC_WH` executed **72.7 s** of queries and
billed **1.1188 credits** — execution was under 2% of what was paid; the rest was the 60-second
minimum per resume and the idle tail before auto-suspend. Three configuration facts keep that
ratio high: the warehouse runs as **Gen2 by default** (`STANDARD_GEN_2`, a higher credit rate per
hour, chosen by a platform default, not by a decision); the ten gate tasks run **on the
warehouse**, so each firing pays a full minute for two sub-second `INSERT`s; and the Dagster
sensor can trigger a full `dbt run` + `dbt test` **every minute** during a burst. All objects are
also created by hand-run SQL, so none of this is reproducible on another account.

The account v3 runs on (`GWHUBCF-QQ53235`, created 2026-11-17) confirms the defaults are not an
accident of the old account: on day one, every warehouse the platform provisioned was Gen2, had
query acceleration enabled, and `COMPUTE_WH` had a 300-second auto-suspend; no resource monitor existed.

#### Success Criteria

Total cost = warehouse credits (`SNOWFLAKE.ACCOUNT_USAGE.WAREHOUSE_METERING_HISTORY`) +
serverless task credits (`SNOWFLAKE.ACCOUNT_USAGE.SERVERLESS_TASK_HISTORY`), per UTC day,
over the measurement window, same load profile for A and B.

- [ ] **H1 (falsifiable):** total credits/day of config B ≤ **75%** of config A.
- [ ] **H2 (falsifiable):** warehouse resumes/day of config B ≤ **50%** of config A
      (`ACCOUNT_USAGE.WAREHOUSE_EVENTS_HISTORY`, resume events).
- [ ] **Freshness guardrail:** p95 delay from source commit to Gold ≤ *N* + 5 min under load in config B.
- [ ] **Idle property preserved:** over ≥ 6 h with no source traffic, 0 warehouse credits and
      < 0.01 serverless task credits.
- [ ] **No drift:** `terraform plan` on `main` after `apply` reports no changes.

If H1 or H2 is not met, the feature still ships: the deliverable is the measured result with
its method. The README states the number we got, not the number we hoped for.

## Part 6 — DEFINE: SCD2_RESTAURANTS

### DEFINE: SCD Type 2 for Restaurants — reference case (SCD2_RESTAURANTS)

> Keep the full history of each restaurant, derived from the CDC event log already stored in
> Bronze, and prove it matters with a Gold model that attributes each sale to the restaurant as
> it was at the time.

#### Metadata

| Attribute | Value |
|-----------|-------|
| **Feature** | SCD2_RESTAURANTS |
| **Date** | 2026-11-17 |
| **Author** | Christian (with Claude) |
| **Status** | Draft — awaiting approval |
| **Clarity Score** | 13/15 |
| **Approved by** | — |

---

#### Problem Statement

`silver_restaurants` keeps only the current state of each restaurant (`upsert` strategy in
`resolve_cdc`). `gold_revenue_per_restaurant` aggregates **all historical sales** against that
current state, so when a restaurant changes city, cuisine or rating, its past revenue is silently
re-labelled with today's attributes. Nobody can answer "what did this restaurant look like when
this sale happened", or "when did it leave the platform". The information is not lost: Bronze is
append-only (ADR-0025) and keeps every CDC event with `op`, `source_ts_ms` and `kafka_offset`.
It is just never modelled.

This is a **single reference case by design**: one domain, one Gold consumer, one ADR that any
other domain can follow when a business need appears.

---

#### Target Users

| User | Role | Pain point |
|------|------|------------|
| Analyst | Reads Gold | Revenue by attribute (city, cuisine) is wrong for any restaurant that changed |
| Auditor / client | Needs traceability | Cannot reconstruct a restaurant's state at a past date |
| Reviewer / hiring manager | Reads the repo | Wants to see SCD2 done from CDC, with tests that prove it |

---

#### Goals

| Priority | Goal |
|----------|------|
| **MUST** | Full version history of restaurants, rebuilt deterministically from Bronze |
| **MUST** | No change for existing consumers of `silver_restaurants` |
| **MUST** | A Gold model that uses the history (point-in-time attribution), with an enforced contract |
| **MUST** | Tests that prove the history is well-formed and agrees with the current state |
| **COULD** | Collapse versions that differ only in untracked columns |

---

#### Requirements

| ID | Requirement | Priority | Verified by |
|----|-------------|----------|-------------|
| REQ-01 | `resolve_cdc` gains a fourth strategy, `scd2`, alongside `upsert`, `append` and `log`, without changing the behaviour of the other three. Output: one row per CDC event per key, with `valid_from`, `valid_to` (NULL = open), `is_current`, `is_deleted`. Ordering uses the existing tie-break (`source_ts_ms`, then `kafka_offset`), ascending. Tombstones (null key) are excluded; a delete event closes the history (`is_deleted = TRUE`, not current). | MUST | AT-001, AT-002, AT-003 |
| REQ-02 | New model `silver_restaurants_history`, versioned by the CDC key (`uuid`), using the `scd2` strategy. | MUST | AT-001 |
| REQ-03 | `silver_restaurants` keeps its current columns and grain (one row per `uuid`, deleted rows absent). Whether it becomes a view over the history or stays an `upsert` table is a DESIGN decision; either way a test proves the two agree. | MUST | AT-004 |
| REQ-04 | New model `gold_revenue_by_restaurant_version`: each order item is attributed to the restaurant version valid at the item's event time. `gold_revenue_per_restaurant` stays unchanged. | MUST | AT-005, AT-006 |
| REQ-05 | The new Gold model has an **enforced dbt model contract** (named, typed columns), as the repo's reference data contract. | MUST | AT-007 |
| REQ-06 | Tests on the history: at most one `is_current` row per key; no overlapping intervals per key; consecutive versions are contiguous (`valid_to` = next `valid_from`). | MUST | AT-002 |
| REQ-07 | A deterministic fixture issues known changes to restaurants in Postgres (attribute updates on ≥ 3 restaurants, ≥ 1 delete) and the changes travel the full CDC path. | MUST | AT-001, AT-003 |
| REQ-08 | ADR: "SCD2 derived from the CDC event log, not from dbt snapshots — applied to one domain as the reference". | MUST | AT-008 |
| REQ-09 | Versions whose tracked columns hash identically to the previous version are collapsed. | COULD | — |

---

#### Success Criteria

- [ ] For the fixture, every changed restaurant has exactly (number of applied changes + 1)
      versions in `silver_restaurants_history`, and the deleted one ends with `is_deleted = TRUE`.
- [ ] 100% of order items in `gold_revenue_by_restaurant_version` match exactly one restaurant
      version, or carry an explicit `unmatched` flag. Zero items match two versions.
- [ ] Total revenue in `gold_revenue_by_restaurant_version` equals total revenue in
      `gold_revenue_per_restaurant`: history changes **attribution**, never the sum.
- [ ] The three history tests (REQ-06) and the reconciliation test (REQ-03) pass on a full
      rebuild, run twice with identical results (determinism).

#### Acceptance Tests

| ID | Scenario | Given | When | Then |
|----|----------|-------|------|------|

| AT-002 | Well-formed intervals | History built | Tests run | One current row per key; no overlaps; contiguous intervals |
| AT-003 | Delete closes the history | Fixture deletes one restaurant | Build | Its last row has `is_deleted = TRUE`, `is_current = FALSE`; it is absent from `silver_restaurants` |
